# Tower v0.4.0 release readiness

Updated: 2026-08-06

## Decision

Status: **prepared locally, not ready or authorized for external publication**.

The repository now identifies the next package as `@tower-org/cli@0.4.0`, has a
versioned changelog section, and produces the changelog with the existing
portable assets. The legacy milestone tags were renamed separately as recorded
below. No main-branch push, release tag, ruleset, workflow dispatch, npm publish,
GitHub Release, or remote asset mutation was performed by this preparation.

## Local hardening completed

- Root and portable dependency manifests identify `0.4.0`.
- Release gates and published smoke derive the version from the root manifest;
  installation documentation uses an `X.Y.Z` placeholder instead of a stale
  release constant.
- Built-in Claude, Codex, and Gemini Providers plus the Qwen sample accept Tower
  `>=0.3.0 <1.0.0`; the previous `<0.4.0` ceiling would have rejected this release.
- `CHANGELOG.md` is copied into Candidate and production asset sets, covered by
  `SHA256SUMS`, and its `0.4.0` section feeds generated release notes.
- Candidate ref/commit values enter the shell through `env`, not direct workflow
  expression interpolation.
- Production publication requires exactly one downloaded npm tarball before it
  calls `release.sh`.
- GitHub publication creates or resumes a draft, uploads and verifies the full
  asset set, and only then publishes it. This is compatible with Immutable
  Releases and remains recoverable before publication.
- Public documentation no longer contains real company-chat screenshots or
  version-specific `0.3.x` guide pages.
- Legacy annotated tags `v1.0` and `v1.1` were replaced remotely by
  `milestone-1.0` and `milestone-1.1` at the same commits with their original
  messages, tagger identity, and timestamps. The local-only `v1.2` was replaced
  by local-only `milestone-1.2` under the same constraints.

## External blockers

These facts were read from GitHub on 2026-08-06:

1. `origin/main` is 20 commits behind local `main` before this working-tree
   preparation. The newest remote CI run is still the failed run for
   `92b4929fd23fe7a6f8ec6669828e37d5e72ddfdb`. Local tests do not replace green
   CI on the final pushed commit.
2. `tower-org/tower` reports no repository rulesets. A tag ruleset must match
   release tags and restrict both updates and deletion before `v0.4.0` is made.
3. Immutable Releases is disabled (`enabled: false`). Enable it before the
   production workflow so the published tag and assets become immutable. The
   tag ruleset is still required to protect the pre-publication window.
4. The current GitHub Pages deployment still serves the removed company-chat
   image URL. Deploy the rebuilt documentation and require that URL to return
   `404` before announcing `0.4.0`; removing it from the working tree alone does
   not update the public site or purge Git history.
5. `npm-production` currently allows the sole reviewer to approve their own
   deployment. That is an accepted single-maintainer tradeoff only if OWNER
   explicitly accepts it; it is not two-person review.

## Go/no-go sequence

1. Review and commit the local `0.4.0` preparation without unrelated working-tree
   changes.
2. Push the reviewed main branch and require green CI plus a green five-target
   Candidate run on the exact commit.
3. Create and verify an active `v*` release-tag ruleset that restricts updates
   and deletions. Enable Immutable Releases for the repository.
4. Deploy the documentation, verify that the removed image URL returns `404`,
   and confirm the changelog date/content and final asset list.
5. With separate OWNER authorization, create and push annotated tag `v0.4.0`.
6. With separate OWNER authorization, dispatch `release.yml` from `v0.4.0` with
   confirmation `@tower-org/cli@0.4.0`.
7. Approve `npm-production` only after prepare, all five native portable jobs,
   and assembly are green.
8. Verify npm provenance, GitHub notes, `CHANGELOG.md`, installers, five portable
   archives, and every `SHA256SUMS` entry; then run published-package smoke.

## Recovery boundary

Local `release:publish` is intentionally not an emergency path: npm provenance
requires the GitHub Actions OIDC identity. If npm succeeds and GitHub asset upload
fails, rerun the same workflow for the unchanged protected tag while artifacts
are retained. Never move the tag, overwrite conflicting assets, or reuse the
version for another commit.
