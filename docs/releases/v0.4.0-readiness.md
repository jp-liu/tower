# Tower v0.4.0 release readiness

Updated: 2026-08-06

## Decision

Status: **prepared and remotely validated, but not authorized for external publication**.

The repository now identifies the next package as `@tower-org/cli@0.4.0`, has a
versioned changelog section, and produces the changelog with the existing
portable assets. The preparation is pushed to `main`, CI and a five-platform
Release Candidate have passed, repository release protections are active, and
the documentation is deployed. No `v0.4.0` tag, npm publication, or GitHub
Release has been created; those remain separate OWNER-authorized operations.

## Local hardening completed

- Root and portable dependency manifests identify `0.4.0`.
- Release gates and published smoke derive the version from the root manifest;
  installation documentation uses an `X.Y.Z` placeholder instead of a stale
  release constant.
- Built-in Claude, Codex, and Gemini Providers plus the Qwen sample accept Tower
  `>=0.3.0 <1.0.0`; the previous `<0.4.0` ceiling would have rejected this release.
- `CHANGELOG.md` is copied into Candidate and production asset sets, covered by
  `SHA256SUMS`, and its `0.4.0` section feeds generated release notes.
- Candidate ref/commit values enter the shell through `env`, not direct workflow
  expression interpolation.
- Production publication requires exactly one downloaded npm tarball before it
  calls `release.sh`.
- Candidate and production workflows expose only `tower-npm-pack-<identity>` plus separate
  `tower-macos-*`, `tower-linux-*`, and `tower-windows-*` artifacts. Assembly
  validates the complete set without publishing a redundant all-platform bundle.
- GitHub publication creates or resumes a draft, uploads and verifies the full
  asset set, and only then publishes it. This is compatible with Immutable
  Releases and remains recoverable before publication.
- Public documentation no longer contains real company-chat screenshots or
  version-specific `0.3.x` guide pages.
- Legacy annotated tags `v1.0` and `v1.1` were replaced remotely by
  `milestone-1.0` and `milestone-1.1` at the same commits with their original
  messages, tagger identity, and timestamps. The local-only `v1.2` was replaced
  by local-only `milestone-1.2` under the same constraints.

## Verified repository controls

These facts were read from GitHub on 2026-08-06:

1. `main` is pushed and its CI `test` and extension-catalog jobs are green.
2. Active ruleset `Protect release tags` matches `refs/tags/v*`, rejects tag
   updates and deletion, and has no bypass actor.
3. Immutable Releases is enabled for `tower-org/tower`.
4. GitHub Pages is deployed, the removed company-chat image URL returns `404`,
   and the documentation root returns `200`.
5. The five-platform Release Candidate passed native build plus offline Node 22
   and Node 24 smoke on macOS arm64/x64, Linux arm64/x64, and Windows x64.

## Remaining publication decisions

1. OWNER must separately authorize creation and push of annotated tag `v0.4.0`.
2. OWNER must separately authorize dispatch of `release.yml` from that tag.
3. `npm-production` allows the sole reviewer to approve their own deployment.
   This is a single-maintainer confirmation, not independent two-person review.
4. Before tagging, re-confirm green CI and Candidate evidence on the exact final
   commit; a newer commit invalidates earlier exact-commit evidence.

## Go/no-go sequence

1. Re-confirm green CI plus a green five-target Candidate run on the exact final
   commit.
2. Confirm the changelog date/content and final independent asset list.
3. With separate OWNER authorization, create and push annotated tag `v0.4.0`.
4. With separate OWNER authorization, dispatch `release.yml` from `v0.4.0` with
   confirmation `@tower-org/cli@0.4.0`.
5. Approve `npm-production` only after prepare, all five native portable jobs,
   and assembly are green.
6. Verify npm provenance, GitHub notes, `CHANGELOG.md`, installers, five portable
   archives, and every `SHA256SUMS` entry; then run published-package smoke.

## Recovery boundary

Local `release:publish` is intentionally not an emergency path: npm provenance
requires the GitHub Actions OIDC identity. If npm succeeds and GitHub asset upload
fails, rerun the same workflow for the unchanged protected tag while artifacts
are retained. Never move the tag, overwrite conflicting assets, or reuse the
version for another commit.
